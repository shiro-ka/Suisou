## §1 適用範囲

**対象**: wixdex / Mado / YTaq / TABaq / 自作 Linux ディストロのデスクトップシェル。

**スコープ外**: タイポグラフィ / スペーシング / 角丸・影の値 / モーション / アイコンセット / **ドメイン色**。

### ★ドメイン色を Suisou に持たない（2026-08-21 決定。一度実装して撤回した）

WIXOSS のカード5色のように**対象物側で固定され作者が動かせない色**。§1 は長く「第4分類として
追加する」と予告していて、wixdex 移行のときに実際に実装した（`DOMAIN_HUE` / `DOMAIN_L`、
`--suisou-wixoss-*`）。動いたし破綻も0件だったが、**その日のうちに撤回した**。

しろさまの指摘:「**ドメイン色は wixdex 独自のもの（Suisou で言うところの「現場で使うもの」）だから、
Suisou で頑張らんでも手書きでいい**」。

撤回した理由:

- **Suisou は「しろかが作ったと分かる」体系。** WIXOSS のカード色は WIXOSS のもので、
  しろかのものではない。`--suisou-wixoss-red` という名前自体がその矛盾を露呈していた
- **掟「3回書いてから足す」を自分で破っていた。** 客は wixdex 1つだけ
- **全プロダクトが5色を運ぶ。** Mado もブログもディストロも、使わない色を配布物に抱える
- **唯一の実利が空振りだった。** solve.py に載せて得られるのは「テーマに追従する彩度」だが、
  wixdex は `hadal × clown` 固定でテーマ切替を持たない。**誰も使わない機能のために
  体系を太らせていた**

**代わりにどうするか**: 現場が自分の CSS に oklch を直書きする。値は設計時に一度計算すれば
足りる（Suisou が `solve.py` → `palette.css` でやっていることの、現場版）。

★**仕組みは残す価値がある**（将来ほかの現場で要ったときの手順）:

```
H   対象物から来る。動かせない
L   面に載せて読める明度。階段ごとに固定
C   maxC(L, H) × 彩度比 × テーマのトーン倍率
検証 非文字なので 3.0:1（WCAG 1.4.11）
```

★実装して分かったこと: **彩度比は色ごとに違う**。ほとんどは 1.0（振り切る）でよいが、
**白だけ 0.36** ―― 白は彩度の無さがアイデンティティで、上限まで振ると
ただの黄色になった（`#fce92f`）。

★**再検討する条件**: ドメイン色を持つ現場が3つになったとき。そのときは
「Suisou がトークンを持つ」のではなく「**現場ごとの値を解く小さなツール**」の形になるはず。

## §2 前提

| # | 前提 | 理由 |
|---|---|---|
| P1 | **純粋なライトテーマは作らない**。代わりに**明るめの L 階段（dim 系統）を用意する** | ★2026-08-17 のしろさまの判断:「**本当に真っ白背景が嫌い。ユーザーが離れるとしても純粋なライトテーマは作りません**」「**ライトモードユーザーには nord 系の明るめの青グレーを投げる**」。→ 極性は反転しない（明るい文字を暗めの面に載せたまま）が、bg を L26 まで持ち上げた第2の階段を持つ。**bg を L30 より上げると本文 4.5:1 を満たす L が色域外に出る**ので、L26 が実用上の上限帯（§6） |
| P2 | **sRGB を基準に彩度上限を決める** | P3 なら余裕は増えるが、非対応環境で破綻しない側に倒す |
| P3 | **コントラスト基準は WCAG 2.2 AA** | APCA は 2023-07 に WCAG 3 ドラフトから外され、勧告は2028〜2030年頃。★**WCAG 2 は暗背景で過大評価する**既知の欠陥があり、本仕様は直撃領域にある。数値のパスは実機確認の代替にならない |
| P4 | **色だけで情報を伝えない**（WCAG 1.4.1） | 意味色はアイコン・文言と併用 |
| P5 | **テーマ × アクセントの直交性は要件** | ディストロのシェルとアプリ群でエンドユーザーが選ぶため。設計時の探索自由度は要件ではない |

## §3 設計の骨格

| | 絶対に守る | 目標（守れないときは最小限だけ譲る） |
|---|---|---|
| v1.0 | L 階段の値 | （なし） |
| v1.1 | 色域・コントラスト・ΔE | L 階段（text-main のみ可変） |
| **v1.2** | 色域・コントラスト・ΔE | **L 階段（全トークンが同じ扱い）** |

「L 階段は全テーマ共通で固定」は**維持できない約束**だった。同じ L94 でも、面C と H によって色域に入ったり入らなかったりする。守れない約束を持つと破っても気づけない。

★v1.1 は text-main だけを導出に降格しており、「なぜ text-main だけ?」が説明できなかった。**v1.2 では全トークンを「共通の目標階段からの最小逸脱」として扱う**（実際に逸脱するのは今のところ text-main だけだが、扱いを揃えた）。Leonardo 型（制約グラフのみで階段を持たない）には行かない。テーマ間で L が揃う利点を捨てないため。

### 人が決めるもの

```
[1] L 階段（目標値・全テーマ共通）
[2] テーマ … H / 面C / アクセント強さ
[3] アクセント … H だけ
[4] 意味色 … H と L
```

### 導出（人が値を持たない）

```
各トークンの L    = 目標値。色域に入らなければ入る最大まで下げる
accent C          = maxC(0.74, H) × アクセント強さ
accent-active     = L0.71 で C = maxC(0.71, H) × アクセント強さ（再クランプ）
hover-surface     = 中立。面の色相のまま、全面に対し ΔE ≥ 0.03 を満たす最大 L（下向き探索）
selected-surface  = L33（dark）/ L44（dim）で ΔE ≥ 0.055 を満たす最小 C
selected-neutral-surface  = 同 L で面の彩度のまま（アクセントに依存しない中立版）
semantic C        = maxC(L, H) × min(0.95, アクセント強さ + 0.15)
semantic-surface  = selected-surface と同じ導出
focus-ring        = accent / scrim = L8 のアルファ 0.72（on-accent は出力しない。§5）
```

### 制約

```
1. 全トークンが sRGB 色域内（base / active）
2. §11 の全ペアがコントラスト基準を満たす（状態込み）
3. ΔE(accent 各状態, text-sub)  ≥ 0.08
4. ΔE(accent, 各意味色)         ≥ 0.055   ← 実物較正済み
5. ΔE(hover-surface, 全面)      ≥ 0.03
6. ΔE(selected-surface, 全面)   ≥ 0.055
7. |C(selected) − C(hover)|     ≥ 0.02（2段が互いに区別できる）
```

**満たさないアクセントはそのテーマで選択不可**。提出書が理由を表示する。

## §4 なぜ OKLCH か

HSL では「明るさを揃えたまま色相だけ変える」ができない（`hsl(60,100%,50%)` の黄と `hsl(240,100%,50%)` の青は同じ明度指定でも見え方が全く違う）。テーマ切替は「L を揃えて H を振る」が前提なので、HSL では土台から成立しない。

**OKLCH**（2020-12、Björn Ottosson）は L が知覚的にほぼ均等。CIELAB(1976) の青領域の破綻を修正している。Tailwind v4 はデフォルトパレット全体を OKLCH に移行済みで、`oklch()` は Baseline 到達。Tailwind の `zinc` は **H を 285.8〜286.3 に固定し L だけ動かす**設計で、本仕様の面の作り方と同じ。

色相角は HSL とズレる: 赤≈27 / オレンジ≈55 / 黄≈95 / 緑≈148 / シアン≈205 / 青≈255 / 紫≈305 / ピンク≈355。

## §6 L 階段（目標値）— ★2系統

**v1.3 で階段が2系統になった。系統内では共通、系統をまたぐと別。**

★**数値の表は `tools/spec-tables.md`（生成物）を参照**。この仕様書には表を持たない（§15）。

**dim は「ライト志向のユーザーに投げる明るめの階段」**（P1）。極性は反転しない。

- **bg の上限は L30**。L35 以上にすると、overlay 上で本文 4.5:1 を満たす L が 96 以上になり色域から出る
- **dim では accent が L74 → L80 に上がる**。overlay が L45 と明るいため、L74 のままだと overlay 上で 3.13:1 とギリギリになる
- **dim では意味色も上がる**（error 73→85 / warning 82→85 / success 76→83）。代償として **dim の error は `#f4bfbc`（C0.061）と薄い赤**になる。overlay(L45) の上で 4.5:1 を出すには L85 が必要で、L85 では赤に彩度が乗らないため。★実運用で「エラーらしくない」と感じたら、dim では意味色を文言でなく surface + 枠で表現し、文言は `text-main` にする手がある（未実施）

- **`item`(28) は `overlay`(34) より暗い** … 「高度の軸」と「操作可能性の軸」を一本に並べると、モーダル内の入力欄がモーダルより明るくなる。順序で解決した
- **面同士のコントラストは 1.14〜1.47:1** … 意図的。面の分離は border が担保する（WCAG 1.4.11 の対象は「識別に必要な部分」）。§10 のコンポーネント層でデフォルト化する
- **線と文字は「最も明るい面 = overlay(34)」から逆算** … v1.2 では面の L が状態で動かないので、この逆算は hover 中も崩れない
- **`text-disabled`(62) は disabled / placeholder 専用** … overlay 上で 3.23:1。WCAG 1.4.3 の除外規定に依る。v1.0 の `text-faint` から改名したのは、本文に使った瞬間コードレビューで浮かせるため

## §7 テーマ

★**テーマの値と使えるアクセントの一覧は `tools/spec-tables.md`（生成物）を参照**。

**面C が上がるとアクセント強さを下げる理由**: Nord を OKLCH に変換した実測が根拠。Nord は全色が C ≤ 0.121 に収まりトーンが統一されており、そこに Tailwind の `orange-500`（C 0.213）を置くと1色だけ別世界に見える。`zinc` は C≈0.01 でトーン制約が存在しないので鮮烈なアクセントが成立する。

★**`fjord`（旧 nord-ish）は Nord 本家の C 上限を超える**（magenta が 0.150）。これは**明示的な選択**で、しろさまの「nord はあくまで雰囲気の例だから ish でいい」という判断による。厳密に Nord のトーンに収めたい場合はテーマに C 天井 0.121 を制約として足すことになるが、その場合 clown と seal が落ちる。

**トレードオフ**: アクセント強さを下げるほど `ΔE(accent, text-sub)` が縮み、使えるアクセントが減る。`fjord` を ×0.72 まで上げれば9色すべて使えるが、Nord らしさは薄れる。

### ★面の色相をどこに置けるか（2026-08-21 に走査して判明）

テーマを新しく作るときの土地勘。**面の色相は自由には選べない。**

`dark` 階段・`cs`=0.020・`ar`=0.70 で全色相を 5 度刻みに走査した結果:

| 面の色相 | 使えるアクセント | 落ちる色 |
|---|---|---|
| 0〜110（赤〜黄〜オリーブ） | **9/9** | |
| 120〜160（緑） | 8/9 | teal |
| 170〜250（シアン〜青） | 7/9 | teal, jelly |
| 260〜285（青紫） | 8/9 | jelly |
| 290〜355（紫〜マゼンタ） | **9/9** | |

**法則は2つ。**

1. **面を色づけるほど、面の色相に近いアクセントを食う。**
   選択下地は「面と ΔE 0.055 以上離れた同色相の色」なので、面自身が同じ方向に
   色を持っていると差が詰まる。`hadal`（cs 0.006）が 9/9 で `fjord`（cs 0.030）が
   6/9 なのはこれ。**9色全部を使いたいなら面は無彩色に寄せる**しかない。

2. **teal と jelly は構造的に余裕がない。**
   選択下地は `tint`（L33）に置くが、その明度で出せる最大 C が
   teal 0.0576 / jelly 0.0577 しかない ―― 目標 0.055 に対して余裕ほぼゼロ。
   他は turtle 0.080 / blue 0.109 / coral 0.169 / seal 0.136 と余裕がある。
   だから面の色相をシアンに寄せた瞬間、真っ先にこの2色が落ちる。

   **明度で払うことはできない。** `tint`(33) の上下は `item`(28) `overlay`(34)
   `hover`(解いて L19) で埋まっていて、動かす余地が無い。彩度で払うしかなく、
   その彩度が色域で頭を打っている ―― これは基準の厳しさではなく色域の形の問題。

★**深海のデザインシステムなのに、海の色（シアン〜青）が面の色相として一番不利**という
ねじれがある。名前が水域なのは中身の色ではなく「深さ＝光の届かなさ」の比喩なので
（`hadal` が h286 のほぼ無彩色であるように）、そこは矛盾しない。

## §8 アクセント

```
orange 55 / turtle 122 / teal 188 / jelly 212 / blue 255
indigo 282 / coral 308 / magenta 332 / seal 355
```

- **L は 74 固定**、**C = maxC(0.74, H) × アクセント強さ**
- **信号機カラー（赤・黄・緑）を持たない**。そこは意味色の領分で、衝突したらアクセント側が譲る（意味色は動かせないため）

**なぜ L=74 か（実測）**: 全色相を1つの L で賄うには「最も弱い色相の上限が最大になる L」が最適。

| L | 最弱色相の上限 | 平均 |
|---|---|---|
| 70 | 0.120 (jelly) | 0.183 |
| **74** | **0.126 (jelly)** | 0.170 |
| 78 | 0.114 (blue) | 0.155 |

**なぜ C を絶対値で固定しないか**: L74 での上限は magenta 0.250 / orange 0.182 / jelly 0.129 と倍近く違う。C を 0.15 で固定すると jelly は色域外、magenta は上限の60%になる。上限比で持つことで、どの色相も同じ度合いで振り切る。副次的に色域外が発生しない。

## §9 意味色

| | H | L | 根拠 |
|---|---|---|---|
| `error` | 22 | **73** | L70 では overlay 上 4.06:1 で本文基準を割る。L73 で 4.59:1 |
| `warning` | 90 | **82** | 黄は L82 以上でないと黄色に見えない（L60 だとオリーブ `#a1790c`） |
| `success` | 155 | 76 | |

**C = maxC(L, H) × min(0.95, アクセント強さ + 0.15)**。完全固定にすると `fjord` のようにトーンを抑えたテーマで意味色だけが浮きすぎる。`+0.15` により**アクセントより常に強い**ままテーマのトーンに従う。

**意味色は状態を持たない**（hover / active しない）。destructive なボタンは v1.2 のスコープ外。

## §10 実装

### 状態の規約

```
hover    : 面の L は動かさない。hover-surface を敷く
selected : selected-surface（または selected-neutral-surface）。
           ★左端2pxのアクセント線は「形」で決まる（2026-08-20 実物判定）――
           既定の行は下地のみ、ruled（連なる一覧）は下地 + 線
active   : --suisou-accent-active（C は再クランプ済み）
focus    : outline: 2px solid var(--suisou-focus-ring); outline-offset: 2px
disabled : --suisou-text-disabled。本文には使わない
```

**hover を「面を明るくする」でやらない理由**（v1.0 の実測）: (a) アクセントが色域外になる（`hadal` で6色）、(b) hover した overlay(L39) の上で line-weak が 1.24:1、line-strong が 2.53:1 に落ちる、(c) accent の hover(L79) が text-sub(L78) と**コントラスト 1.00:1** になる。「C を濃くする」案も teal で ΔC 0.019 と JND 未満のため不採用。

**focus の輪が accent と重ならない理由**: `focus-ring = accent` なので、accent で装飾された
要素にフォーカスが当たると同色が隣接して消えうる。実装は `outline-offset: 2px` ――
輪と要素の間に下地が 2px 見えるので、距離で分離できている（v1.2 で書いていた
「bg の 1px を挟む二重 box-shadow」はこの形に置き換えた）。

### コンポーネント層 ＝ 安定化する契約

**利用側が触るのは `data-suisou-*` 属性であってトークンではない。** §6 の「border 必須」と
§5 の「text-disabled は disabled 専用」を、規約ではなくデフォルトにする（`pages/ui/*.css`）。

★v1.2 でここに書いていたクラス案（`.panel` / `.field` …）は **data 属性の部品に置き換えた**。
凍結対象は **`CONTRACT.md`（生成物）にある属性・値・トークン・既定の目録**で、
破壊的変更はその目録で判定する。

### CSS の形

切替は `data-suisou-theme` と `data-suisou-accent` の2属性（**必ず同じ要素に書く**。
`lint_css.py` が両方向の単独指定を検査する）。アクセントの C・accent-active・下地・
text-main の L・意味色はすべて**計算済みの確定値**を書き出す（CSS では `maxC` を
計算できないため）。色域外の組み合わせだけ出力されず、推奨しない組は★コメント付きで出る（掟2 の運用）。

## §13 既知の制約・未解決

### A. 根拠の質

- **`SEM_OFFSET = 0.15`** … 目分量。「意味色はアクセントより一段強く見せる」という意図で置いた値で、逆算ではない
- **ΔE フロア** … `semantic` は **2026-08-17 に実物較正済み（0.058 が区別可能 → 0.055）**。`hover`(0.03) / `selected`(0.055) / `textSub`(0.08) は未較正の目分量

### B. 数値上の弱点

- **`accent`(L74) と `text-sub`(L78) が近い**。ΔE フロアは満たすが、グレースケールにするとほぼ同じ明るさ。アクセントは枠線・下線・配置と併用する前提
- **アクセント9色に近いペアがある**（magenta–seal 23度 / coral–magenta 24度 / teal–jelly 24度）
- **`turtle` が鮮やかにならない**。L74 では黄系の色域が狭い。L 固定を選ぶ限り構造的に解決しない
- **`line-weak`(1.51:1) と `error`(4.59:1) が基準ギリギリ**
