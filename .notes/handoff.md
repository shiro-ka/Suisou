## Suisou とは

## ★このリポジトリの掟

### 1. 色を決めるのは `tools/solve.py` だけ

色の値をどこにも手で書かない。CSS にも仕様書にも書かない。

```
python3 tools/solve.py          # 生成（palette.css / suisou.data.js / spec-tables.md）
python3 tools/solve.py --check  # 検証のみ。破綻があれば exit 1
```

数値の表は `tools/spec-tables.md`（生成物）にある。**`.notes/palette-spec.md` は散文と判断の理由だけを持ち、表を持たない。**

理由: 設計中、「ツール(JS) / Python / 仕様書の表」の3つが同じ数値を主張して同期が手作業だった結果、**色域チェック漏れ・トークン数の誤記・検証ペアの欠落**という3つのバグを出した。真実の源泉は1つにする。

### 2. 守るものと譲るもの

```
絶対に守る … 色域内
推奨の条件 … コントラスト基準 / ΔE フロア
目標（譲る）… L 階段の値
```

「L 階段は全テーマ共通で固定」は**維持できない約束**だった（同じ L94 でも面C と H によって色域に入ったり入らなかったりする）。守れない約束を持つと、破っても気づけない。制約を先に置き、L は最小限だけ譲る。

#### ★2026-08-20 改訂: 「使えない」をやめて「推奨しない」にした

もとは基準を1つでも割ると **CSS に出さない**（＝その組み合わせは存在しない）扱いだった。
`tint` を下げて罫の穴を塞いだとき、代償として `trench × jelly` が使えなくなり、
しろさまの判断で運用を変えた。

> 使えないは厳しすぎるきがする。「見づらいのでオススメしません」って言うぐらいでいいんでないの

実際、落ちていた4組の理由を調べると**色域外は0件**で、全部「区別しにくい」系だった。

```
trench × jelly    選択下地が面と近い ΔE 0.050（目標 0.055）
fjord  × jelly    同 0.051
fjord  × blue     accent が text-sub と近い ΔE 0.067（目標 0.08）
fjord  × indigo   同 0.067
```

**壊れてはいない。** だから2層に分けた。

| | 意味 | CSS に出すか | `--check` |
|---|---|---|---|
| `blocking` | **色域外**。意図した色が表示できず、ブラウザが勝手に丸める | **出さない** | 落ちる |
| `issues` | 見づらい・紛らわしい | **出す**（★コメント付き） | 落ちない |

- `resolve_tint` はフロアに届かなくても `None` を返さず、**届く限りの最大 C** を返す
- コントラストのペア検査は**推奨する組だけ**を対象にする。推奨しない組が基準を割るのは
  当たり前なので二重に数えない
- `suisou.data.js` が `recommended` と `warnings` を持ち、プレビューは押せなくする代わりに
  **破線＋★＋理由**を出す

★これで「基準を割った瞬間に組み合わせが消える」ことがなくなった。今後 L の段をいじっても、
**壊れるのではなく推奨から外れる**だけになる。

### 3. 設計の入力は4つだけ

```
[1] L 階段（2系統: dark / dim）
[2] テーマ … H / 面C / アクセント強さ の3つ
[3] アクセント … H だけ
[4] 意味色 … H と L
```

残りは全部導出。人が値を持たない。

### 4. Suisou 本体に JS を持ち込まない

配布の最終形が「CDN に置いて `<link>` 1本」なので、**JS が要る部品は
それだけで配布形態を壊す**。現時点で `pages/ui/` の8ファイルは全部 CSS で、
`addEventListener` も `querySelector` も1つも無い。この状態を守る。

- `app.js` はプレビューサイト専用、`suisou.data.js` は `solve.py` の生成物。
  どちらも配る対象ではない
- **部品を1つ足すたびに「JS が要るか」を確認する。** 要るなら作らないか、
  別の形にする
- モーダルは `<dialog>`、開閉は `details` / `popover` 属性で足りることが多い。
  pickker は画像モーダルを `<dialog>` でやっている
- スクロールバーの自前描画を見送ったのはこの掟のため（詳細は「決まっていること」の
  スクロールバーの項）

### 5. しろさまとの進め方

- **しろさまはスライダーを触らない。** こちらが制約を解いてパレットを提出し、しろさまは実物を見て「紫もうちょい明るく」のような指示を出す。**それを数値に翻訳するのはこちらの仕事**
- **未検証で自信満々が最大の地雷。** 数値を出すときは必ず計算して確かめる。「たぶん」で断定しない
- **実物判定はしろさまの言葉が正。** ΔE フロアが 0.055 なのは、実物を見て「0.058 でも区別できる」と判定したから
- **wixdex だけを見て設計しない。** 適用先にはブログ・規約などの長文も含まれる。一度 h4〜h6 を「UI では使わないから」と潰しかけて、指摘で撤回した

## 決まっていること

- **色** … 4テーマ × 9アクセント。**36通り全部を CSS に出し、うち32が推奨**。構造的破綻0件。詳細は `.notes/palette-spec.md`
  - 33 だったのを 32 に減らした。選択下地（`tint`）の上に載る罫が未検査で
    掟2（コントラスト基準）を破っていたため、`tint` を L36 → L33 に下げて塞いだ。
    `trench × jelly` は L35 の時点で選択下地の解を失う。**両立する L は存在しない**ので、
    掟2 を優先して組み合わせを1つ捨てた。既定の `hadal × jelly` は無事
- **タイポ** … サイズ `12/14/16/20/24/28/32`、行間は4の倍数の2系統、ウェイト3段（`400/500/700`。★2026-08-20 に 600 を廃止 ―― Zen Maru Gothic が 600 を持たず 700 で描画されていた）。詳細は `.notes/type-spec.md`
- **線形デザイン** … 塗らない（CTA すらアウトライン）。美学であると同時に、テーマ切替を技術的に成立させている柱
- **影は使わない**（★2026-08-20 改訂。もとは「実際に浮くもの＝モーダル・ポップアップだけ」と書いていた）。
  美学ではなく**ダーク専用では影が機能しない**ため。影は下地を暗くする技法だが、
  Suisou の下地は既に暗いので暗くする余地が無い。実測（hadal、panel L22 の上）:

  ```
  Tailwind の shadow-xl（黒 α0.10）   輝度比 1.02   何も起きていない
  一番濃い scrim（α0.72）             輝度比 1.14   自前の一番緩い基準 1.5 にも届かない
  白い光 α0.15                        輝度比 3.45   効く
  line-strong を罫に回す              輝度比 3.10   ← これを採用
  ```

  暗い側で効くのは**光の方**なので、白いグロウは理屈では正しい。ただし
  `line-strong` を罫に回すとほぼ同じ強さになる ―― つまり**Suisou の罫は、
  ぼかしていない白い光**。足すと同じものが二重になって輪郭が濁るので足さない。
  Linear などが内側に白い光を入れるのは罫が極端に薄いからで、罫を 3:1 で引く
  Suisou には代用品が要らない。

  例外は**画像の上に浮くもの**（下地の明るさが読めない。白の上なら scrim は 3.18 で効く）。
  `overlay` の仕事ではないので 3回書いてから足す。そのときの値は黒 α0.10 ではなく scrim ベース
- **ダーク専用**。純粋なライトテーマは作らない。ライト志向のユーザーには `dim` 系統（明るめの階段）を投げる
- **角丸**（★2026-08-20 決定）… 3段。**太さではなく「対象の高さ」で選ぶ**。

  ```
  --suisou-radius-small  4px   行内コードのような背の低いもの
  --suisou-radius        8px   面・ボタン・入力欄・コードのかたまり
  --suisou-radius-pill   999px Avatar・Tag・見出しの帯
  ```

  8px は高さ 32px 前後の部品に合わせた値で、**高さ 20px の行内コードに当てると
  高さの4割が丸まってカプセルに見え、Tag と見分けがつかなくなる**。だから小さい
  ものには 4px。`small` という語は `--suisou-icon-small` と揃えてある。

  それまで 4px は `code.css` に直書きされていて段の外にあった。値は既にあったので、
  **概念を足したのではなく、あったものに名前を付けた**。

- **モーション**（★2026-08-20 決定）… 段は2つだけ。

  ```
  --suisou-motion-fast: 120ms   色だけ動くもの（hover / 選択 / 押下 / 罫）
  --suisou-motion:      200ms   現れる・消えるもの（overlay / scrim）
  --suisou-ease: cubic-bezier(0.2, 0, 0, 1)
  ```

  決め方は「**動く距離が大きいほど長くする**」。Suisou は面を塗らず罫で示すので
  **位置が動く要素がほとんど無く**、色だけが変わる。だから速い方に倒した。
  120ms は Carbon の fast-02（110）と Bootstrap の既定（150）の間。
  イージングは ease-out 系 ―― ユーザーが起こした動きは始まりを速くすると
  「押した瞬間に反応した」感じになる。

  - **焦点の輪は動かさない。** キーボード操作では即座に出てほしいため
  - **`prefers-reduced-motion` はトークンを潰すだけ。** 全部品がトークン経由で
    時間を取っているので、`*` や `!important` を使わずに済む
  - **overlay の出入りは JS なし。** `display` / `overlay` を `allow-discrete` で繋ぎ、
    `@starting-style` で開く直前の姿を与える。未対応なら animate しないだけ

- **スクロールバー** … 標準の2プロパティだけ。根（`[data-suisou-root]`）に1回書いて継承させる

  ```css
  scrollbar-width: thin;
  scrollbar-color: var(--suisou-line-strong) transparent;
  ```

  検討したのは主に**アプリ型**（チャット・管理画面のように画面が固定高で、
  panel の中が巻物になる形）。ここでは panel 内スクロールが主になるので、
  "ページのバーは常時出ている" 前提の他フレームワークの流儀がそのままは使えない。
  **文書型**（ブログ・利用規約のように panel が縦に積まれてページ全体が動く形）は
  普通にビューポートのバーになるので、この検討は当てはまらない。Suisou は両方やる。

  - **`scrollbar-gutter` は使わない。** `stable` は溝が右にしか空かず左右の余白が食い違う。
    `both-edges` は両側に空く分だけ中身が痩せる。どちらも「常に変」で、
    バーが出るときだけ 10px 動く方がまだ普通に見えた
  - **角丸との干渉は問題にならない。** 溝を透明にしてあるので、削られるのは
    何も描かれていない領域だけ。実際に見えるつまみは端まで届かない。
    「面を塗らず線1本だけ見せる」という線形デザインの副産物
  - **`::-webkit-scrollbar` は書かない。** Firefox で効かない。
    wixdex はこれで作り込んでいたが（`track { margin }` で端を空け、
    `thumb { border: transparent + background-clip }` で線を細くする）、
    Firefox では素のバーのままだった
  - **自前描画は見送り。** CSS だけ（`animation-timeline: scroll()`）は
    Firefox が preview のみ（MDN の compat data で確認）。JS 10行なら全ブラウザで
    「罫に接する・角を避ける・幅を食わない・長さが比例する」が全部取れるが、
    配布物に JS が増える。必要になったらここから再開する

## prose（★2026-08-20 実装。見出しの罫だけ未決）

Markdown が吐いた素の HTML に属性を書けないので、包む側に1つだけ付けて
中の要素に直接当てる仕組み。

**`base.css` の「要素セレクタは使わない」を破る唯一の場所**。
`[data-suisou-prose]` の内側に閉じているので漏れない ―― 破っていい場所を
1つだけ用意して封じ込める形。

### 作り方（案C を採った）

**部品を先に作って、prose がそれを束ねる。** 各部品ファイルが
`[data-suisou-prose] :where(…)` を自分のセレクタに並べているので、
**値が2箇所に散らない**。`prose.css` が持つのは「大きさの割り当て」と
「縦のリズム」だけで、新しい見た目を1つも発明していない。

| 要素 | 誰が持つか |
|---|---|
| `a` | `ui/link.css` |
| `code` / `pre` | `ui/code.css` |
| `blockquote` | `ui/quote.css` |
| `ul` / `ol` | `ui/list.css` |
| `table` | `ui/table.css` |
| 見出し・段落・リズム・`hr` / `img` / `dl` | `ui/prose.css` |

この順で作った: Table → Link → Code → Quote / List → prose。

### 縦のリズム

**見出しは「前を広く、後ろを詰める」。** 前の話題から離し、次の内容に近づける。
タイポの定石で、**段を増やす前にまずこれを当てた**結果、`space-4`（24px 相当）
までで足りて新しい段が要らなかった。

```
             既定            tight
ふつうの間   space-3（16）   space-2（8）
見出しの前   space-4（24）   space-3（16）
見出しの後   space-2（8）    space-1（4）
```

### 2段ある

- `data-suisou-prose` … 記事。本文 16px（pickker）
- `data-suisou-prose="tight"` … panel の中の短文。本文 14px（wixdex のデッキメモ）

### 見出しの帯（★2026-08-20 決定）

pickker の形を出発点に7案を並べて、**帯を左にぶら下げる形**に着地した。

```
h1  28/700  帯なし    記事のタイトルは1つしかないので区別が要らない
h2  24/700  6px accent   いちばん強い
h3  20/600  3px accent
h4  16/600  3px 薄
h5  16/500  1px 薄
h6  14/600  帯なし    14px という大きさ自体がしるし
```

**pickker の形が「イケてない」理由を4つに分解した**のが出発点:

| どこが | なぜ |
|---|---|
| アクセント色 | Suisou のアクセントは「操作できるもの」の色。押せない見出しが同じ強さで主張する |
| 左罫と下罫が二重 | 同じ仕事を2本でやっている |
| 6px という太さ | Suisou の罫は 1px と 3px だけ |
| 見出しだけ字下げ | 中身の左端が揃わない。pickker は `margin-left: -.5rem` で誤魔化している |

このうち**アクセント色だけは残した**（しろさまの判断）。他の3つは解いた。

- **`border` ではなく `::before`。** `border-left` は箱ごと角丸になるので
  カプセル型にできない。絶対配置なら箱が動かず、入れ物の余白にも依存しない。
  擬似要素を1つ使うが、markdown のアンカーリンクは `<a>` を挿入する方式が
  主流なのでぶつかりにくい
- **6px の縛りは消えた。** `::before` で描く帯は罫（border）ではなく**図形**なので、
  1px / 3px の罫の体系の外にある
- **字下げしない。** 帯は本文の左端より外に出るので、見出しの文字は本文と揃う
- **帯は階層を「担う」のではなく補強する。** 主役はサイズとウェイトなので、
  h3 と h4 が同じ 3px でも 20px と 16px の差が先に効く。6段に6種類は要らない
- 帯と文字の間はどの段も `space-2`。**太さが違っても右端が揃い、太いものだけが左へ伸びる**

★`type-spec` が h5 / h6 に置いていた「字下げする左罫」は**外した**。
帯と二重になるため。あれは「段が7つしかないので下2段を罫で区別する」ための
ものだったが、帯が階層を担うなら役目が重なる。`app.js` の `ROLES_DOC` からも外した。

★**固定 URL が要る理由**: Suisou を直すたびに現場の見た目が黙って変わるのは困る、

### 移す順番（★2026-08-20 の検討。数字は実測）

```
1. いま         GitHub Pages のまま。現場が1つなので /v/<sha7>/ で足りる
2. 2つ目が来たら  /v1/ チャンネルを足す。★ホスティングより先に痛くなる
3. 気になったら   Cloudflare に移す。_headers 3行で済む
```

**3 が最後**。キャッシュ10分と brotli 無しは、この規模だと体感できない。

#### 帯域と ToS は問題にならない

```
1回の読み込み        4,619 バイト（gzip 後の実測）
100GB/月 のソフト上限 = 2,300万回/月 = 77万回/日
全プロダクト合計 2万回/日 でも上限の 2.6%
```

桁が3つ違う。**帯域は一生問題にならない。** ToS も自分のプロダクト数個なら無風。

#### ★「共通 CDN ならキャッシュを共有できる」は成り立たない

ブラウザの HTTP キャッシュは**トップレベルのサイトごとに分割**されている
（Chrome 86 / Firefox 85 以降。トラッキング防止のため）。

```
wixdex が読む suisou.css → wixdex 用の枠
Mado が読む   suisou.css → Mado 用の別枠。落とし直す
```

同じ URL でも共有されない。**プロダクトが増えても CDN に移す動機にはならない。**

#### 本当に効くのはバージョン方針

プロダクトが増えて困るのはホスティングではなくこれ。

```
wixdex /v/4d55065/  Mado /v/9ff5e96/  YTaq /v/54425db/  ブログ /v/f71ec28/
```

**どれがどの版か分からなくなり、Suisou を直すたびに全箇所の SHA を書き換えて回る。**
いま `/v/<sha7>/` しか無いのは現場が1つだから成立している。

2つ目が来たらチャンネルを足す。

```
/v/<sha7>/   完全固定。動かない（いまある）
/v1/         v1 系の最新。★破壊的変更のときだけ動く
```

普段は全プロダクトが `/v1/` を指し、Suisou を直せば自動で行き渡る。
凍結したい現場だけ `/v/<sha7>/` を指す。

★**そのとき「破壊的変更とは何か」の定義が要る。** 値の名前を変える
（`cols` → `stretch`、`fill` → `grow`、`floating` → `overlay`、`on` → `aria-pressed`）、
既定を変える（`block` ボタンの寄せ、flex の子を `none` に）など、
**この会話だけで何度もやっている**。ルールが無いと `/v1/` が信用できない。

#### Cloudflare に移すときに得られるもの

| | GitHub Pages（実測） | Cloudflare |
|---|---|---|
| キャッシュ | `max-age=600` 固定。**ヘッダを設定できない** | `immutable, max-age=1年` を付けられる |
| 圧縮 | gzip のみ | brotli（CSS でさらに15〜20%） |
| 配信 | Fastly（`via: 1.1 varnish`）。CDN としては本物 | 同等 |

移行コストは低い。**URL の形（`/v/<sha7>/…`）が決まっているので origin が変わるだけ**で、
`_headers` を1つ置けば済む。

```
/v/*
  Cache-Control: public, max-age=31536000, immutable
```

（`/dist/`（移動する方）は `max-age=600` が正しいので、いまの GitHub Pages は
**半分だけ偶然合っている**）

## 配布の最終形（Cloudflare。まだやらない）

最終的には **Cloudflare に置いて、`<link>` / `@import` 1本で読める形**にしたい。
実装はずっと後だが、途中の判断がここに効くので先に書いておく。

- **配るのは結合された1ファイル。** いま `pages/index.html` が `ui/*.css` を
  並べているのは開発の都合。1ファイル単位で配れる状態は保つが、
  出荷形はまとめたもの。`@import` は直列に落ちるので、CDN でも結合が正解
- **`helpers.css` は別ファイルのまま。** 任意（他にユーティリティがあるなら読まない）なので、
  本体に混ぜない
- **色は同梱できる。** `palette.css` は全テーマ × 全アクセントを持っていて、
  切り替えは `data-suisou-theme` / `data-suisou-accent` なので、1ファイルで足りる
- **★JS を要求する部品は重い。** `<link>` 1本が目標なら、JS が要る部品は
  それだけで配布形態を壊す。スクロールバーの自前描画を見送ったのはこの筋
  （そのときは「JS が増える」としか書いていないが、本当の理由はここ）
- **バージョン付き URL が要る。** 掟1 の生成物を含むので、
  `solve.py` を直した日と配信物がずれない仕組みが要る

### 全部入りか、1組だけか（実測。まだ決めない）

gzip 後のバイト数。`ui/*.css` はコメントを除いた値。

```
ui/*.css                        1,766
palette.css 33組ぜんぶ           2,605
palette.css hadal × orange だけ    518

現場が読む合計   全部入り 4,382 ／ 1組だけ 2,205   ← 半分になる
```

`palette.css` の構造は「テーマ本体 1,525 バイト × 4」＋「アクセント 355 バイト × 33」。
`solve.py` が吐いているので、**組み合わせごとのファイルを出すのはループを1つ足すだけ**。
配布形式ではなく生成の問題なので、後から足せる。

- **全部入り** … テーマ切替ができる（`data-suisou-theme` を書き換えるだけ）
- **1組だけ** … 半分。ただし切替を捨てる
- ★二択にすると困る場合がある。`prefers-color-scheme` に反応させたい現場は
  `hadal` + `shoal` の2組が要る（`shoal` はライト志向向けの `dim` 階段）。
  「1組 or 全部」ではなく「選んだ組だけ」にしておく方が安全

## Tailwind を消せる形に育てる（2026-08-22 の測定）

しろかさんの願い ――「将来的にちゃんと Tailwind 消しても Suisou で wixdex ぐらい
作りたい」。急がないが、距離は測ってある。

### いまの距離

wixdex に残る class は **853 箇所 / 259 種**。分解するとこうなる。

| 塊 | 数 | Suisou が持つべきか |
|---|---|---|
| 色 | 112 | **持つべき**。`@theme` ブリッジ依存なので Tailwind 撤去で真っ先に死ぬ |
| 配置 | 〜300 | **半分は持つべき**（`layout` の守備範囲） |
| 余白 | 〜160 | **持つべき**（段は既にある） |
| 実寸 | 〜160 | 持たない。現場のもの（`aspect-[12/17]` など） |
| タイポ | 〜120 | **持つべき**（`data-suisou-text` の守備範囲） |

**8割は原理的に Suisou 側**。「残す予定の薄い層」は実は 160 前後しかない。

★撤去の順序は固定される: **色 112 → 幾何 740 → Tailwind 撤去**。
  色クラスはブリッジ（Tailwind の機能）があって初めて Suisou の色になるので、
  先に Tailwind を抜くと 112 箇所が一斉に無色化する。

### 構造的に欠けている3つ

3回ルールでは出てこない。**現場は Tailwind があるから困らず、需要が可視化されない**ため。

1. **レスポンシブの語彙**（wixdex で 58 箇所・5段）
   Suisou の `layout` は `md:` `lg:` しか持たない。wixdex は `sm` `xl` `2xl` も使う。
   ここが埋まらないと現場は必ず Tailwind に戻る。**最大の穴。**
   段をいくつ持つかは設計判断（Suisou が5段持つのか、2段に絞って現場に譲るのか）。

2. **余白を「1箇所だけ置く」手段**
   段（4/8/16/24）はあるが `layout` の gap 経由でしか使えない。`mb-2` 相当がない。
   `helpers.css` は「Tailwind 併用時は入れるな」と書いてあり、
   **併用をやめた先の道具がない**。衝突しない名前空間での再設計が要る。

3. **リセット**
   Suisou は「要素セレクタを使わない」掟でリセットを持たない。
   Tailwind の preflight（配信 CSS 25KB のうち **11KB**）が消えると `box-sizing` も無くなる。
   掟の例外を1つ作る必要がある ―― `prose` が既に
   「破っていい場所を1つだけ用意して封じ込める」形をとっているので前例はある。

### ★この見立ては n=1

**上の3つは wixdex 1つだけを見て出した結論**。客が増えれば変わる。

実際、**Suisou の `layout` は19語あるのに wixdex は4語（`row` `stack` `between` `end`）しか
使っていない**。未使用は:

```
aside body center container even foot frame grow head hold
nowrap screen scroll start stretch wrap
```

画面の骨格（`frame` / `head` / `aside` / `body` / `foot`）が丸ごと未検証。
wixdex が単画面のツールで、シェルを持たないため。

### 次の客は Mado

- ダッシュボード型・**13画面**。`DashboardShell` / `Header` / `Sidebar` / `Footer` /
  `InfoNav` / `UserCard` を持つ ―― **まさに未使用の骨格語彙を最初に試す客**
- `tailwind-variants` + `tailwind-merge` を使っている（wixdex の cva と同じ問題）
- `src/lib/components/ui/` に自前の小さなデザインシステムがある
