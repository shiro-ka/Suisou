## ★このリポジトリの掟

### 1. 色を決めるのは `tools/solve.py` だけ

色の値をどこにも手で書かない。CSS にも仕様書にも書かない。

```
python3 tools/solve.py          # 生成（palette.css / suisou.data.js / spec-tables.md）
python3 tools/solve.py --check  # 検証のみ。破綻があれば exit 1
```

数値の表は `tools/spec-tables.md`（生成物）にある。**`.notes/palette-spec.md` は散文と判断の理由だけを持ち、表を持たない。**

理由: 設計中、「ツール(JS) / Python / 仕様書の表」の3つが同じ数値を主張して同期が手作業だった結果、**色域チェック漏れ・トークン数の誤記・検証ペアの欠落**という3つのバグを出した。真実の源泉は1つにする。

### 2. 守るものと譲るもの

```
絶対に守る … 色域内
推奨の条件 … コントラスト基準 / ΔE フロア
目標（譲る）… L 階段の値
```

「L 階段は全テーマ共通で固定」は**維持できない約束**だった（同じ L94 でも面C と H によって色域に入ったり入らなかったりする）。守れない約束を持つと、破っても気づけない。制約を先に置き、L は最小限だけ譲る。

#### ★2026-08-20 改訂: 「使えない」をやめて「推奨しない」にした

もとは基準を1つでも割ると **CSS に出さない**（＝その組み合わせは存在しない）扱いだった。
`tint` を下げて罫の穴を塞いだとき、代償として `trench × jelly` が使えなくなり、
しろさまの判断で運用を変えた。

> 使えないは厳しすぎるきがする。「見づらいのでオススメしません」って言うぐらいでいいんでないの

実際、落ちていた4組の理由を調べると**色域外は0件**で、全部「区別しにくい」系だった。

```
trench × jelly    選択下地が面と近い ΔE 0.050（目標 0.055）
fjord  × jelly    同 0.051
fjord  × blue     accent が text-sub と近い ΔE 0.067（目標 0.08）
fjord  × indigo   同 0.067
```

**壊れてはいない。** だから2層に分けた。

| | 意味 | CSS に出すか | `--check` |
|---|---|---|---|
| `blocking` | **色域外**。意図した色が表示できず、ブラウザが勝手に丸める | **出さない** | 落ちる |
| `issues` | 見づらい・紛らわしい | **出す**（★コメント付き） | 落ちない |

- `resolve_tint` はフロアに届かなくても `None` を返さず、**届く限りの最大 C** を返す
- コントラストのペア検査は**推奨する組だけ**を対象にする。推奨しない組が基準を割るのは
  当たり前なので二重に数えない
- `suisou.data.js` が `recommended` と `warnings` を持ち、プレビューは押せなくする代わりに
  **破線＋★＋理由**を出す

★これで「基準を割った瞬間に組み合わせが消える」ことがなくなった。今後 L の段をいじっても、
**壊れるのではなく推奨から外れる**だけになる。

### 3. 設計の入力は4つだけ

```
[1] L 階段（2系統: dark / dim）
[2] テーマ … H / 面C / アクセント強さ の3つ
[3] アクセント … H だけ
[4] 意味色 … H と L
```

残りは全部導出。人が値を持たない。

### 4. Suisou 本体に JS を持ち込まない

配布の最終形が「CDN に置いて `<link>` 1本」なので、**JS が要る部品は
それだけで配布形態を壊す**。現時点で `pages/ui/` の8ファイルは全部 CSS で、
`addEventListener` も `querySelector` も1つも無い。この状態を守る。

- `app.js` はプレビューサイト専用、`suisou.data.js` は `solve.py` の生成物。
  どちらも配る対象ではない
- **部品を1つ足すたびに「JS が要るか」を確認する。** 要るなら作らないか、
  別の形にする
- モーダルは `<dialog>`、開閉は `details` / `popover` 属性で足りることが多い。
  pickker は画像モーダルを `<dialog>` でやっている
- スクロールバーの自前描画を見送ったのはこの掟のため（詳細は「決まっていること」の
  スクロールバーの項）

### 4. しろさまとの進め方

- **しろさまはスライダーを触らない。** こちらが制約を解いてパレットを提出し、しろさまは実物を見て「紫もうちょい明るく」のような指示を出す。**それを数値に翻訳するのはこちらの仕事**
- **未検証で自信満々が最大の地雷。** 数値を出すときは必ず計算して確かめる。「たぶん」で断定しない
- **実物判定はしろさまの言葉が正。** ΔE フロアが 0.055 なのは、実物を見て「0.058 でも区別できる」と判定したから
- **wixdex だけを見て設計しない。** 適用先にはブログ・規約などの長文も含まれる。一度 h4〜h6 を「UI では使わないから」と潰しかけて、指摘で撤回した

## 決まっていること

- **色** … 4テーマ × 9アクセント。**36通り全部を CSS に出し、うち32が推奨**。構造的破綻0件。詳細は `.notes/palette-spec.md`
  - 33 だったのを 32 に減らした。選択下地（`tint`）の上に載る罫が未検査で
    掟2（コントラスト基準）を破っていたため、`tint` を L36 → L33 に下げて塞いだ。
    `trench × jelly` は L35 の時点で選択下地の解を失う。**両立する L は存在しない**ので、
    掟2 を優先して組み合わせを1つ捨てた。既定の `hadal × jelly` は無事
- **タイポ** … サイズ `12/14/16/20/24/28/32`、行間は4の倍数の2系統、ウェイト4段。詳細は `.notes/type-spec.md`
- **線形デザイン** … 塗らない（CTA すらアウトライン）。美学であると同時に、テーマ切替を技術的に成立させている柱
- **影は「実際に浮くもの」だけ**（モーダル・ポップアップ）。面の分離は border が担保する
- **ダーク専用**。純粋なライトテーマは作らない。ライト志向のユーザーには `dim` 系統（明るめの階段）を投げる
- **スクロールバー** … 標準の2プロパティだけ。根（`[data-suisou-root]`）に1回書いて継承させる

  ```css
  scrollbar-width: thin;
  scrollbar-color: var(--suisou-line-strong) transparent;
  ```

  検討したのは主に**アプリ型**（チャット・管理画面のように画面が固定高で、
  panel の中が巻物になる形）。ここでは panel 内スクロールが主になるので、
  "ページのバーは常時出ている" 前提の他フレームワークの流儀がそのままは使えない。
  **文書型**（ブログ・利用規約のように panel が縦に積まれてページ全体が動く形）は
  普通にビューポートのバーになるので、この検討は当てはまらない。Suisou は両方やる。

  - **`scrollbar-gutter` は使わない。** `stable` は溝が右にしか空かず左右の余白が食い違う。
    `both-edges` は両側に空く分だけ中身が痩せる。どちらも「常に変」で、
    バーが出るときだけ 10px 動く方がまだ普通に見えた
  - **角丸との干渉は問題にならない。** 溝を透明にしてあるので、削られるのは
    何も描かれていない領域だけ。実際に見えるつまみは端まで届かない。
    「面を塗らず線1本だけ見せる」という線形デザインの副産物
  - **`::-webkit-scrollbar` は書かない。** Firefox で効かない。
    wixdex はこれで作り込んでいたが（`track { margin }` で端を空け、
    `thumb { border: transparent + background-clip }` で線を細くする）、
    Firefox では素のバーのままだった
  - **自前描画は見送り。** CSS だけ（`animation-timeline: scroll()`）は
    Firefox が preview のみ（MDN の compat data で確認）。JS 10行なら全ブラウザで
    「罫に接する・角を避ける・幅を食わない・長さが比例する」が全部取れるが、
    配布物に JS が増える。必要になったらここから再開する

## prose（★後回し。ちゃんと練る必要がある）

Markdown が吐いた素の HTML に属性を書けないので、包む側に1つだけ付けて
中の要素に直接当てる仕組み。Tailwind Typography の `prose` と同じ役目。

**`base.css` の「要素セレクタは使わない」を破る唯一の場所**になる。
`[data-suisou-prose]` の内側に閉じているので漏れない ―― 破っていい場所を
1つだけ用意して封じ込める形。Media が既に小規模に同じことをしている
（`[data-suisou-media-content] :where(header)`）。

### ★満たすべき条件（しろかさんの言）

> pickker みたいなブログでも、wixdex のメモとかでも違和感ないデザインにする必要がある

実例は両方すでにある。**段が2つ要る**という話になりそう。

| | 何 | いまの実装 |
|---|---|---|
| wixdex | デッキメモ。**panel の中に入る短文** | `marked` + DOMPurify → `class="prose prose-invert prose-sm"`、`border + bg-zinc-600/10 + p-4` の箱の中 |
| pickker | **記事まるごと**。目次つき | `markdown-it` → `h2` に左罫6px＋下罫、`h4` に左罫3px、リンクカード |

### 中身の大半はもう決まっている

`type-spec` の「長文」の段（`app.js` の `ROLES_DOC`）をそのまま素の要素に配るだけ。

```
h1 28/700  h2 24/700  h3 20/600  h4 16/600
h5 16/500 + 左罫       h6 14/600 + 左罫弱
p 16/400 doc（行間 +4px）        small 14/400
```

新しく決めるのは扱っていないもの ―― `ul` / `ol` / `blockquote` / `code` / `pre` /
`a` / `hr` / `table` / `dl` / `img`。作例に残っている `.demo-code`（行内コード）と
`.demo-defs`（定義リスト）がその前哨。

## 配布の最終形（★まだやらない。判断の足しにするだけ）

最終的には **Cloudflare に置いて、`<link>` / `@import` 1本で読める形**にしたい。
実装はずっと後だが、途中の判断がここに効くので先に書いておく。

- **配るのは結合された1ファイル。** いま `pages/index.html` が `ui/*.css` を
  並べているのは開発の都合。1ファイル単位で配れる状態は保つが、
  出荷形はまとめたもの。`@import` は直列に落ちるので、CDN でも結合が正解
- **`helpers.css` は別ファイルのまま。** 任意（他にユーティリティがあるなら読まない）なので、
  本体に混ぜない
- **色は同梱できる。** `palette.css` は全テーマ × 全アクセントを持っていて、
  切り替えは `data-suisou-theme` / `data-suisou-accent` なので、1ファイルで足りる
- **★JS を要求する部品は重い。** `<link>` 1本が目標なら、JS が要る部品は
  それだけで配布形態を壊す。スクロールバーの自前描画を見送ったのはこの筋
  （そのときは「JS が増える」としか書いていないが、本当の理由はここ）
- **バージョン付き URL が要る。** 掟1 の生成物を含むので、
  `solve.py` を直した日と配信物がずれない仕組みが要る

### 全部入りか、1組だけか（実測。まだ決めない）

gzip 後のバイト数。`ui/*.css` はコメントを除いた値。

```
ui/*.css                        1,766
palette.css 33組ぜんぶ           2,605
palette.css hadal × orange だけ    518

現場が読む合計   全部入り 4,382 ／ 1組だけ 2,205   ← 半分になる
```

`palette.css` の構造は「テーマ本体 1,525 バイト × 4」＋「アクセント 355 バイト × 33」。
`solve.py` が吐いているので、**組み合わせごとのファイルを出すのはループを1つ足すだけ**。
配布形式ではなく生成の問題なので、後から足せる。

- **全部入り** … テーマ切替ができる（`data-suisou-theme` を書き換えるだけ）
- **1組だけ** … 半分。ただし切替を捨てる
- ★二択にすると困る場合がある。`prefers-color-scheme` に反応させたい現場は
  `hadal` + `shoal` の2組が要る（`shoal` はライト志向向けの `dim` 階段）。
  「1組 or 全部」ではなく「選んだ組だけ」にしておく方が安全

### 文書型（pickker）で分かったこと

Blogger 用の Pico CSS テーマ。`src/style.css` 133行。

- **本文はページが動く。脇は箱の中で動く。** 目次（`max-height: 100dvh`）、タグのポップオーバー、
  モバイルのドロワーの3箇所が内部スクロール。「ページが動く／動かない」の二択ではなく混在する
- **スクロールバーの指定は133行中ゼロ。** 文書型では何も要らない
- **ライトテーマと、画面幅で変わるルート文字サイズは Suisou の比較対象にしない。**
  前者は「配布する Blogger テーマ」という制約から、後者は Pico の設計（16→21px の段階）から来ている

### 一貫していたもの（wixdex ∩ pickker）

別々に、なんとなく作られたのに揃っていた。線形デザインを柱に置いた根拠になる。

- **丸ゴシック**。wixdex は `Zen Maru Gothic`（Suisou と同一）、pickker は `M PLUS Rounded 1c`
- **塗りが薄い。** wixdex で最頻の面は `bg-zinc-600/10`（不透明度10%）が17回。
  pickker は Pico の塗りを `background: none` で剥がしている。**足す／剥がすと逆から来て同じ場所に着いている**
- **ボタンは罫なし・透明・弱い文字色・hover で面が出る**
- **タグはピル。** wixdex `rounded-full` 9回、pickker `border-radius: 999px`

揃っている項目のほとんどが「**やらないこと**」で、足す側の合意は丸ゴシックとピルくらい。
好みとして安定していたのは避け方の方だった。

（左罫の見出しは pickker だけ。wixdex の `border-l` は2回で様式になっていないので、
Suisou の `data-suisou-text~="rule"` は pickker 側の発明）
